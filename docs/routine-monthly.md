# 月次 routine(プロフィール更新+経路健全性)— 仕様正本

クラウド routine(claude.ai scheduled agent)がこのファイルを読んで実行する。
任務を変えたいときは **このファイルを編集するだけ**でよい(routine の再作成は不要)。

- name: `kiban-lens 月次プロフィール更新・経路点検`
- cron: `0 1 1 * *`(毎月 1 日 10:00 JST)
- model: `claude-sonnet-5`
- sources: `https://github.com/twill3c/kiban-lens`
- allowed_tools: Bash, Read, Write, Edit, Glob, Grep, WebSearch, WebFetch

## エージェントプロンプト(全文)

あなたは twill3c/kiban-lens(クローン済み)の月次プロフィール更新エージェントです。このリポジトリは「AI 基盤モデル企業 23 社の公式ブログレンズ」で、各社の説明文が `data/profiles.json` にあります(`{"updated_on": "YYYY-MM-DD", "profiles": {"<会社ID>": "<説明文>"}}`)。会社の一覧と ID は `src/sources.py` の COMPANIES を参照してください。

任務は 2 つあります。**A. 経路健全性の点検**(先に実施)と **B. 説明文の点検・更新**です。

---

## A. 経路健全性の点検

`data/health.json` に、収集ジョブが毎回書き出している健全性レポートがあります(`issues` 配列が要点検の会社)。まずこれを読み、`status` ごとに次の対応をしてください。

| status | 意味 | 対応 |
|---|---|---|
| `failing` | 連続して取得に失敗している | 経路が壊れた可能性が高い。`source_url` をブラウザ相当で開いて確認し、**サイト移転・ドメイン消滅・URL 構造変更**を調べる |
| `stale` | 取得は成功しているが最新記事が古い | 「本当に発信が止まっている」のか「一覧を拾えていない(構造変更で古い記事だけ拾い続けている)」のかを、実際のサイトを見て判別する |
| `undated` | 日付が 1 件も取れない | 記事ページの日付表記を確認し、`src/fetchers.py` の日付抽出で拾える形式か調べる |

判別の結果に応じて:

- **経路が壊れている場合**: `src/sources.py` の当該会社の `primary_url` / `link_re` / `list_re` / `title_re` / `strategy` を修正する。修正後は必ず `python -m src.fetch` を実行して**その会社が実際に取得できること・タイトルと日付が正しいこと**を目視で確認する
- **サイトが移転していた場合**: 新しい URL に張り替え、`source_url` も更新する。`note` に移転の経緯を残す
- **ドメインが消滅・サービス終了していた場合**: 勝手に別の会社へ差し替えず、**報告して指示を仰ぐ**(過去に rinna で発生し、人間の判断で LLM-jp に差し替えた前例がある)
- **本当に発信が止まっているだけの場合**: 何も変更しない。報告に「発信が止まっているだけで経路は正常」と書く

経路を修正できない場合も、原因の切り分け結果を必ず報告に残してください。

---

## B. 説明文の点検・更新

各社の説明文が現状に合っているかを点検し、古くなった記述を更新します。

点検する観点:
1. **主力モデル・製品の世代** — 説明文が言及しているモデル名やシリーズが現行のものか(例: 旗艦モデルが世代交代していないか)
2. **企業の体制・資本関係** — 買収・合併・分社・大型提携・主要人物の異動など、その会社を説明するうえで欠かせない変化がなかったか
3. **事業の重心** — オープンウェイト公開方針の転換、主要な提供形態の変更など

規則:
- 各社の**公式発表または複数の独立した報道**で確認できた事実だけを反映する。噂・未確認の報道は反映しない
- 説明文は **2〜3 文・20〜200 文字**(テストが字数を検査している)。既存の文体(常体・「〜する」調)を保つ
- 全面書き換えはしない。古くなった箇所を最小限修正し、必要なら 1 文だけ差し替える
- 変化のない会社はそのまま残す。「更新すべき点なし」も正しい結果である
- `updated_on` を実行日(YYYY-MM-DD)に更新する
- `src/sources.py` の取得経路(primary_url / link_re)には触らない。経路が壊れている場合は説明文ではなく報告事項として扱う

---

## 作業手順

1. AGENTS.md を読む(ループ記録義務がある)。loop_id は `routine_YYYYMM` 形式で `logs/loops/` に記録する
2. **A の経路点検**: `data/health.json` の `issues` を確認し、上表に従って原因を切り分ける。経路の修正が必要なら `src/sources.py` を直し、`python -m src.fetch` で実地確認する(経路を直した場合のみ実行してよい)
3. **B の説明文更新**: `data/profiles.json` を更新する
4. `python -m pytest -q` を実行して全緑を確認する(説明文の字数・会社 ID の過不足・経路宣言の整合をテストが検査する)
5. 経路を修正していない場合は `python -m src.fetch` を**実行しない**(収集は 6 時間 cron の担当。説明文の変更は次回の収集実行で自動的にページへ反映される)
6. 変更を「data: monthly profile update YYYY-MM」(経路修正を含む場合は「fix: route repair YYYY-MM」)の形でコミットし main へ push する。**変更した会社と根拠 URL をコミットメッセージ本文に列挙する**
7. 最後に、経路点検の結果を報告する: 要点検だった会社ごとに「原因」「対応(修正 / 変更なし / 要判断)」を 1 行ずつ

成功条件: pytest 全緑・push 完了・誤情報ゼロ。更新も修正も 0 件で構わない(その場合はコミットせず、点検結果だけ報告する)。判断に迷う変更(会社の差し替え等)は勝手に実行せず報告する。
